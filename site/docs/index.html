Architecture Relays & Hosting Security & DevSecOps Development & CI

1. Architecture & Product Model

Chirp provides secure, intuitive remote desktop assistance between two people who trust each other. Its core architecture is deliberately simple:

  • Single Binary: One identical executable across Windows, macOS, and Linux. No background services, no system drivers installed, and no account registrations.
  • Peer-to-Peer First: Connections establish direct WebRTC encrypted channels whenever network topology permits, falling back to stateless relays only when NAT traversal requires it.
  • Strict One-Way Direction: The person needing help provides a connection code. The helper enters the code and can only view or control after explicit on-screen consent is granted.
  • Single-Use Ephemeral Codes: Connection codes and links are single-use tokens that expire immediately upon connection. Even if a code is intercepted after a session begins, it cannot be reused.

For more details on the interaction flow, see the Product Model.

2. Relays & Self-Hosting

The Chirp public network consists of stateless relays designed for zero persistence and radical data minimization:

  • Volatile Memory Only: Relays hold connection matchmaking states strictly in RAM. Session data is never written to disk, databases, or object storage.
  • No Traffic Decryption: Screen sharing, audio, input, and file transfer payloads are end-to-end encrypted. Relays forward blind data packets without access to plaintext content.
  • Run Your Own Relay: Any organization or individual can host their own relay without licensing restrictions. The relay binary compiles cleanly from deploy/relay and runs behind any TLS termination or reverse proxy.
  • Independent Network Status: The public relay health is monitored every 30 seconds from external probes at status.usechirp.app.

3. Security, Privacy & DevSecOps

Security is the foundation of Chirp’s design rather than an afterthought:

  • Zero Telemetry & No Cookies: No analytics, tracking pixels, or third-party SDKs exist in either the application or the website.
  • Strict Web CSP & Trusted Types: The website enforces default-src 'none', disallows HTML sinks (0 innerHTML), and requires trusted-types 'none' to eliminate Cross-Site Scripting (XSS).
  • Cryptographic Signing: Release binaries are verified and signed using Sigstore Cosign, providing cryptographic transparency and provenance.
  • Privacy Safeguards: Passwords copied from password managers are automatically sanitized and never synchronized across remote clipboards.
  • Responsible Disclosure: Vulnerability reports follow RFC 9116 and should be sent to security@fabrintek.com.br.

Review our complete policies in Privacy & Terms and the Code of Conduct.

4. Development, CI & Contributing

Chirp is 100% open source under the AGPL-3.0 license. We welcome contributions that align with our security and simplicity goals:

  • Branching Strategy: All active development takes place in isolated feature branches (feature/*, fix/*) targeting main via pull requests.
  • Developer Certificate of Origin (DCO): Every commit must include a sign-off (git commit -s) certifying origin and license compliance.
  • Automated CI Gates: Every pull request undergoes static analysis (CodeQL, SAST with gosec, govulncheck), secret scanning (Gitleaks), license validation, and Aikido Security review.
  • Join the Community: Participate in architectural proposals, share user stories, or ask technical questions on our Community Hub.
