# Chirp — Handoff Prompt for Continuation Agents

Paste this whole file as the opening prompt of a new agent session on this
repository. It is written to be self-contained: it assumes the agent has the
repo checked out and has read nothing else.

---

## 1. Your role

You are continuing development of **Chirp**, an open-source (AGPL-3.0-only)
on-demand remote support tool owned by **Fabrintek Engenharia Digital Ltda**.
Work on the `develop` branch. Commit with `git commit -s` (a DCO
`Signed-off-by` trailer is mandatory and enforced in CI) and push with
`git push -u origin develop`. Do not open pull requests unless asked.

Read `README.md`, `CONTRIBUTING.md` and `LICENSING.md` before your first
commit. They are not boilerplate — they encode hard constraints (below).

## 2. What Chirp is

A technician generates a 6-digit PIN. The person being helped opens a web page
("the Nest"), enters the PIN, grants explicit consent on their own machine, and
the remote session begins. **No installation, no standing agent, no account.**

This is deliberately the opposite of a persistent-agent RMM product. Every
design decision should be checked against that sentence.

**The session layer is all that exists.** There is no binary, no server, no
transport, no UI. `go build ./...` builds a single library package, whose files
are:

```
session/code.go         PIN generation (crypto/rand, 100000-999999), Format/Normalize
session/consent.go      ConsentRequest / ConsentDecision types, DefaultPermissions
session/session.go      Session, SessionState machine, SessionManager (in-memory)
session/session_test.go tests for the above
```

### The state machine (already implemented)

`pending → connected → consent_requested → consent_granted → active →
terminated`, with `consent_denied` and `expired` as terminal branches.
`SessionManager` holds sessions in a `map` keyed by UUID plus a `codeIndex`
keyed by the 6-digit PIN, reaps expired sessions on a 10-second ticker, and
exposes `Subscribe(code)` returning a channel of snapshots (intended to back
SSE/WebSocket push to the Nest page) and `WaitForConsent(ctx, code)`.

## 4. Known defects

### 4.1 `reapExpired` deadlock — FIXED (`73988a9`)

`reapExpired()` took `sess.mu.Lock()` and then called `sess.Clone()`, which takes
`sess.mu.RLock()`. `sync.RWMutex` is not reentrant, so the reaper blocked
forever while holding `sm.mu` — the first PIN allowed to expire froze the whole
manager. `ListActiveSessions` had the same shape (`RLock` then `Clone`), latent
because recursive read-locking only deadlocks once a writer is queued.

Fixed with an unexported `cloneLocked()` for callers already holding `sess.mu`;
`Clone()` remains the locking wrapper. Every other `Clone()` call site was
audited — all snapshot after unlocking. `reapExpired` also now collects
snapshots under the lock and notifies after releasing it, synchronously, so an
expiry event is observable as soon as it returns.

Regression tests are in `session/reaper_internal_test.go` (package `session`, so
they can drive `reapExpired` directly instead of waiting out its 10-second
ticker). **If you refactor locking here, keep them:** before the fix the first
one does not fail, it hangs until the test binary is killed.

### 4.2 PIN redemption throttling — IMPLEMENTED (`session/redemption.go`)

Redemption is now throttled per origin: `DefaultMaxRedemptionFailures` (5)
failures per `DefaultRedemptionWindow` (10 minutes), tunable via
`SetRedemptionLimit`.

**Note the shape, because the obvious reading of `CONTRIBUTING.md` is wrong.**
Its example commit message says "expire a PIN after three failed redemptions",
but in Chirp the PIN *is* the credential — there is no second secret to get
wrong, so a failed redemption is a guess that hit no live session at all.
Counting failures per session would defend nothing, because the guesses an
attacker makes while sweeping the keyspace belong to no session. The cap is
therefore per caller, which is what bounds how much of the 900,000-code space
one origin can sweep per window.

Consequences to know about:

- **Every code that arrives from the network must be metered.** Use
  `LookupCode(code, origin)` or `ConnectClient`; both draw on the same
  per-origin budget. `GetSessionByCode` is unmetered and is for callers that
  already hold a code legitimately — exposing it to the network turns it into
  an oracle that sweeps the keyspace however tight the limit is. That is not
  hypothetical: the signalling server did exactly that until it was integrated
  (see §4.4).
- **Callers that supply no origin share one bucket**, so a server that forgets
  the address throttles its own users. Deliberate — skipping the limit on an
  empty origin would make the defence opt-out. The signalling server derives
  the origin from the connection; behind a reverse proxy set
  `Server.ClientIP`, or every user shares the proxy's budget.
- A throttled origin is refused even when its next guess is a live code.
- Malformed codes count, so probing has no unmetered channel.
- The limiter's records are reaped alongside expired sessions.

### 4.3 Still open

- `Session` has a `sync.RWMutex` field carrying a `json:"-"` tag, which does
  nothing on an unexported field. Harmless; confirm and simplify.
- `CreateSession` retries PIN generation 10 times against collisions but does
  not distinguish "collision" from "entropy failure"; the error message is
  generic.
- **CodeQL and dependency review are off** until the repository variable
  `CODE_SCANNING` is set. The repository is private, and both need GitHub
  Advanced Security there — confirmed on barahn/chirp#1, where both failed for
  that reason. Each run warns that the gate is off. Set the variable when the
  repository goes public or Code Security is enabled; `docs/devsecops.md`
  explains, including why marking them required before then enforces nothing.
- **Branch protection is written but not applied**, and two decisions block
  applying it. The rules are versioned in `.github/rulesets/`, with the
  reasoning in `docs/branching.md`. Their first version could not have worked —
  `main` required linear history while allowing only merge commits, required
  a check under the wrong name, and would have deadlocked from the second
  release on — and those defects are fixed. What remains is policy: with one
  maintainer, nobody can approve their own pull requests; and `handoff.yml`
  pushes straight to `main`, which the pull-request rule refuses.
- **The handoff refresh needs redesigning before `main` is protected.** A
  bypass for GitHub Actions would let it push, but also let any workflow with a
  write token push to `main`; and each refresh commit lands on `main` without
  reaching `develop`, so the generated block conflicts on every following
  release. The snapshot is fully derivable from the tree, which points at the
  likely answer — regenerate it rather than commit it, or check its freshness at
  pull-request time the way `THIRD_PARTY_NOTICES.md` already works — but the
  runner was asked for explicitly, so this is the maintainer's call.
- **The signalling protocol has no presence notice.** A peer that sends before
  the other end has joined gets a `chirp.error` saying so, and nothing tells it
  when the other end arrives — it can only retry blind. The join window above
  makes this reachable even when both peers dial at once. A `chirp.peer_joined`
  notice sent to the waiting peer is the natural fix; decide it with the
  signed-envelope question (§5.5), since both change what the ends must speak.
- `WaitForConsent` reads from a buffered channel of capacity 1, so only one
  waiter is woken per session. Fine for one technician per session; revisit if
  that stops being true.

### 4.4 What integrating the signalling server exposed — FIXED

The `signalling` package merged cleanly and its tests passed, and it still
reopened two holes where it met the session layer. Both were proven with a probe
against the merged tree before being fixed:

- **An unmetered oracle.** Its HTTP endpoints resolved codes with
  `GetSessionByCode`, so the throttle in `ConnectClient` never ran: fifty wrong
  guesses from one address came back `404` fifty times, and then a live code
  came back `200`. Every code-keyed endpoint — `GET /api/sessions/{code}`,
  `POST .../consent`, and `/ws?code=` — now goes through `LookupCode`, and a
  throttled origin gets `429`.
- **Consent recorded without being asked for.** `SubmitConsent` accepted a
  decision in any state, so `POST .../consent` with `granted:true` on a
  session no machine had joined set it to `consent_granted`. With the oracle,
  whoever guessed a code could consent in the helped person's place. It now
  requires `consent_requested`, which is what the branch's own tests assumed.

**The consequence to know:** nothing over HTTP moves a session to
`connected` or `consent_requested` yet — the server never calls
`ConnectClient` or `RequestConsent`. So the consent endpoint now refuses every
real session until that flow is wired, which is correct: consent that can be
given before it is requested is not consent. Wiring it is the Nest's and
`cmd/chirp`'s job (§5).

Also found: `TestSignallingCrossesBetweenPeers` failed 2 runs in 15 under CPU
load. A client's `Dial` returns when the server writes the upgrade response,
and the server joins the peer to the hub only afterwards, so an offer sent into
that window is refused with `ErrNoPeer` and dropped. The test now waits for both
peers to be registered. The product half is open — see §4.3.

## 5. The roadmap — what is missing, in dependency order

From `README.md`'s own "not here yet" list:

1. **A signalling server — exists** (`signalling/`, integrated in `02cadc3`).
   A two-peer relay plus an HTTP surface, written fresh around
   `SessionManager`; the Barahn one is proprietary and was not ported. Still
   missing from it: driving the session through `connected` and
   `consent_requested` (§4.4), a presence notice (§4.3), and use of
   `Subscribe` as a push channel for session state — the join page polls
   `GET /api/sessions/{code}` instead.
2. **The Nest** — the `/join` page where the end user types the PIN, sees who is
   asking and which permissions are requested (`DefaultPermissions`), and
   allows or denies. Commit `80f5531` mentions a Nest `/join` page but no such
   code is in the tree; assume it must be written.
3. **A `cmd/chirp` binary.** There is no entry point at all yet.
4. **A TURN relay.** Until then, self-hosting means bring-your-own STUN/TURN
   (coturn). Document, do not vendor.

**The remote-session mechanism is not yours to write.** Screen capture, VP8
encoding, input injection, clipboard, file transfer, WebRTC and the reverse
tunnel live in [remotekit](https://github.com/barahn/remotekit) under
Apache-2.0. Chirp consumes it as a dependency. If you find yourself
implementing capture or encoding inside Chirp, stop — it belongs upstream.

Tracking issue / separation plan: the
[barahn/barahn](https://github.com/barahn/barahn) repository.

### 5.5 The remotekit boundary in practice

Chirp does not consume remotekit yet: `go.mod` requires only `google/uuid`, and
on the unmerged signalling branch `gorilla/websocket`. The relationship is
documented and licensed but not instantiated. This section records what an
audit of the two trees actually found, so the next agent does not have to
re-derive it.

**What remotekit already provides** (Apache-2.0, ~15k lines, 14 packages):
`screen` with capture for X11/Wayland/Windows/macOS plus damage detection and a
pure-Go VP8 encoder whose reconstruction is byte-exact against libvpx;
`webrtc` (`PeerSession` over pion, video track, `SignalMessage`); `input`;
`clipboard`; `transfer` (chunked, resumable); `tunnel`; `tray`; `service`;
`osinfo`; `bark` (the shared wire envelope); `heartbeat`.

**`tunnel` is not Chirp's relay, and this is the important negative result.**
It is built around enrolment: pairing codes, persistent agent credentials, an
agent registration store, agent IDs, online status. That is precisely the
standing-agent model Chirp rejects in its first paragraph. Do not try to reuse
it for session signalling; the unmerged `signalling` package writing its own
two-peer hub is the correct call, not duplication.

**What the signalling branch genuinely duplicates: almost nothing.** Its `Hub`
never parses what it forwards — `Forward` relays opaque bytes by design — so it
does not reimplement `webrtc.SignalMessage` encode/decode. Two narrow seams are
worth closing before it merges:

- ~~`encodeError` emits `{"type":"error",...}` into the same namespace as
  remotekit's `SignalType`.~~ Closed: relay messages now use
  `signalling.RelayErrorType` = `"chirp.error"`. A dotted value cannot collide
  with remotekit's bare-word types, and names the relay as the sender.
- Nothing pins Chirp's two *ends* to remotekit's envelope. The hub does not
  care, but the technician viewer and the agent must agree, and today only
  prose says they will.

**The finding that matters most.** remotekit ships
`webrtc/signed.go`: a signed `SignalMessage` — ed25519, domain-separated
canonical bytes (length-prefixed, not JSON, so a browser can reproduce them),
bounded lifetime, clock-skew tolerance and a replay-blocking `NonceCache`.
Signing is opt-in and the fields are `omitempty`, so adopting it breaks no
existing receiver.

Read `remotekit/docs/decentralised-signalling.md` for why it exists: a
signalling server is a man-in-the-middle with total power over a session, and
signing at the endpoints is what demotes the carrier from *trusted component*
to *transport*. That bears directly on one of Chirp's three design
commitments — "any hosted service is a convenience, never a requirement". A
hosted Chirp relay that the endpoints cannot verify around is not a
convenience; it is the trusted third party the commitment says it must not be.

So: **Chirp's signalling hub should be a relay the endpoints do not have to
trust, and remotekit already has the parts.** That is a design decision for the
maintainer, not a defect — but decide it before the Nest and `cmd/chirp` are
written against an unauthenticated envelope, because retrofitting it later means
changing both ends and the relay at once.

One caveat when reading that document: its status line says "proposal, not
accepted. Nothing here has been implemented", and for its Phase 0 item 3
("Extend `SignalMessage` with `PubKey`, `Nonce`, `IssuedAt`, `ExpiresAt` and
`Sig`, plus `Sign()`/`Verify()` and a seen-nonce cache") that is simply out of
date — `webrtc/signed.go` implements exactly that. Trust the tree over the
status line.

**Where the dependency will finally appear:** `cmd/chirp`, the agent side. It
needs `screen`, `input`, `clipboard`, `transfer` and `webrtc.PeerSession`, and
that is the commit where `require github.com/barahn/remotekit` lands. Nothing
in `session/` needs remotekit, and nothing in `session/` should acquire it.

## 6. Hard constraints — do not trade these away

**Product commitments** (from `README.md`, stated as constraints on what Chirp
may become):

- **No feature gates.** Screen sharing, input control, multi-monitor, file
  transfer and clipboard sync are the free core, permanently. Never add a
  licence check, tier check or entitlement lookup around any of them.
- **Explicit consent.** A session cannot start without the end user agreeing on
  their own machine, in a prompt Chirp controls. No "unattended mode", no
  pre-authorisation, no consent bypass flag — not even behind a config key.
- **Self-hostable with zero restrictions.** Anyone may run their own signalling
  and relay. Any hosted service is a convenience, never a requirement. No
  phone-home, no mandatory endpoint.

**Licensing and dependency constraints:**

- Every new Go file starts with:
  ```go
  // SPDX-License-Identifier: AGPL-3.0-only
  // Copyright (C) 2026 Fabrintek Engenharia Digital Ltda
  ```
- **No copyleft dependencies.** Chirp is AGPL, so a GPL/AGPL dependency would
  be licence-*compatible* and still unacceptable: Fabrintek relicenses Chirp
  for its proprietary platform on the strength of owning all of Chirp, and it
  owns none of its dependencies. Permissive only (MIT/BSD/Apache-2.0). CI
  enforces this via `scripts/gen-third-party-notices.sh`; after any dependency
  change, re-run it and commit `THIRD_PARTY_NOTICES.md`.
- **Dependencies point inwards only.** remotekit depends on neither of the
  others; Chirp may depend on remotekit; the Barahn platform may depend on
  both. A change that needs the arrow reversed is a design problem, not a
  licensing exception.
- **Contributions are closed.** Do not merge external pull requests. The DCO
  sign-off CI check is *not* CLA acceptance and must never be described as
  such.

## 7. Working agreement

- Small, reviewable commits with Conventional Commit subjects
  (`feat(session):`, `fix(session):`, `ci:`, `docs(legal):` — follow the
  existing log).
- Every commit signed off: `git commit -s`.
- Tests alongside behaviour; run `go test -race ./...` and `go vet ./...`
  locally before pushing. Prefer a failing test first for each defect in
  section 4.
- Keep `README.md`'s "Status" section honest. It currently says Chirp is not a
  runnable product; when that stops being true, it is part of the same change
  to say so.
