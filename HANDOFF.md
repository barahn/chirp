# Chirp — Handoff Prompt for Continuation Agents

Paste this whole file as the opening prompt of a new agent session on this
repository. It is written to be self-contained: it assumes the agent has the
repo checked out and has read nothing else.

---

## 1. Your role

You are continuing development of **Chirp**, an open-source (AGPL-3.0-only)
on-demand remote support tool owned by **Fabrintek Engenharia Digital Ltda**.
Start each change on a branch from `main` (`feature/*`, `fix/*`, `deps/*`,
`docs/*`) and land it on `main` by pull request, as `docs/branching.md`
describes. Commit with `git commit -s` (a DCO `Signed-off-by` trailer is
mandatory and enforced in CI).

Read `README.md`, `CONTRIBUTING.md` and `LICENSING.md` before your first
commit. They are not boilerplate — they encode hard constraints (below).

**Planned work is tracked on GitHub**, in the issues of this repository and the
[Chirp roadmap](https://github.com/orgs/barahn/projects/2) project, whose
*Track* field orders it. §8 summarises it; when the two disagree, the issues
are the newer record.

## 2. What Chirp is

**Read [`docs/product-model.md`](docs/product-model.md) first — it is the
authoritative description.** In short: one binary, identical on both sides.
Anyone downloads Chirp and runs it; it shows its own code and a share link.
User 2 reads their code (or sends the link) to user 1, user 1 types it into
their own Chirp, user 2 accepts in a prompt on their own machine, and **user 1
controls user 2's machine**. Every use of a link mints a new single-use code.
**No installation, no standing agent, no account.**

That model superseded an earlier one — a technician generated a PIN and the
helped person typed it into a web page, "the Nest". The code now follows the
product model: the session direction was inverted when Chirp adopted
remotekit's `rendezvous` package (§4.5).

This is deliberately the opposite of a persistent-agent RMM product. Every
design decision should be checked against that sentence.

### The state machine (already implemented)

`pending → connected → consent_requested → consent_granted → active →
terminated`, with `consent_denied` and `expired` as terminal branches.
`SessionManager` holds peers and sessions in maps keyed by ID; codes, links and
the throttle live in a `rendezvous.Registry`. It reaps undecided sessions past
their deadline on a 10-second ticker (and calls `Registry.Sweep`), and exposes
`Subscribe(sessionID)` and `WaitForConsent(ctx, sessionID)`. An owner is in at
most one session at a time: a code redeemed while its owner is busy is spent
and returns `ErrPeerBusy`.

## 4. Known defects

### 4.1 `reapExpired` deadlock — FIXED (`73988a9`)

`reapExpired()` took `sess.mu.Lock()` and then called `sess.Clone()`, which takes
`sess.mu.RLock()`. `sync.RWMutex` is not reentrant, so the reaper blocked
forever while holding `sm.mu` — the first PIN allowed to expire froze the whole
manager. `ListActiveSessions` had the same shape (`RLock` then `Clone`), latent
because recursive read-locking only deadlocks once a writer is queued.

Fixed with an unexported `cloneLocked()` for callers already holding `sess.mu`;
`Clone()` remains the locking wrapper. Every other `Clone()` call site was
audited — all snapshot after unlocking. `reapExpired` also now collects
snapshots under the lock and notifies after releasing it, synchronously, so an
expiry event is observable as soon as it returns.

Regression tests are in `session/reaper_internal_test.go` (package `session`, so
they can drive `reapExpired` directly instead of waiting out its 10-second
ticker). **If you refactor locking here, keep them:** before the fix the first
one does not fail, it hangs until the test binary is killed.

### 4.2 PIN redemption throttling — IMPLEMENTED (now remotekit's `rendezvous`)

> Since §4.5 the limiter is remotekit's; Chirp supplies the values (5 per 10
> minutes). `LookupCode`, `ConnectClient` and `GetSessionByCode` no longer
> exist. The rules below hold unchanged — they are the ones `rendezvous`
> implements.

Redemption is now throttled per origin: `DefaultMaxRedemptionFailures` (5)
failures per `DefaultRedemptionWindow` (10 minutes), tunable via
`SetRedemptionLimit`.

**Note the shape, because the obvious reading of `CONTRIBUTING.md` is wrong.**
Its example commit message says "expire a PIN after three failed redemptions",
but in Chirp the PIN *is* the credential — there is no second secret to get
wrong, so a failed redemption is a guess that hit no live session at all.
Counting failures per session would defend nothing, because the guesses an
attacker makes while sweeping the keyspace belong to no session. The cap is
therefore per caller, which is what bounds how much of the 900,000-code space
one origin can sweep per window.

Consequences to know about:

- **Every code that arrives from the network must be metered.** Use
  `LookupCode(code, origin)` or `ConnectClient`; both draw on the same
  per-origin budget. `GetSessionByCode` is unmetered and is for callers that
  already hold a code legitimately — exposing it to the network turns it into
  an oracle that sweeps the keyspace however tight the limit is. That is not
  hypothetical: the signalling server did exactly that until it was integrated
  (see §4.4).
- **Callers that supply no origin share one bucket**, so a server that forgets
  the address throttles its own users. Deliberate — skipping the limit on an
  empty origin would make the defence opt-out. The signalling server derives
  the origin from the connection; behind a reverse proxy set
  `Server.ClientIP`, or every user shares the proxy's budget.
- A throttled origin is refused even when its next guess is a live code.
- Malformed codes count, so probing has no unmetered channel.
- The limiter's records are reaped alongside expired sessions.

### 4.4 What integrating the signalling server exposed — FIXED

The `signalling` package merged cleanly and its tests passed, and it still
reopened two holes where it met the session layer. Both were proven with a probe
against the merged tree before being fixed:

- **An unmetered oracle.** Its HTTP endpoints resolved codes with
  `GetSessionByCode`, so the throttle in `ConnectClient` never ran: fifty wrong
  guesses from one address came back `404` fifty times, and then a live code
  came back `200`. Every code-keyed endpoint — `GET /api/sessions/{code}`,
  `POST .../consent`, and `/ws?code=` — now goes through `LookupCode`, and a
  throttled origin gets `429`.
- **Consent recorded without being asked for.** `SubmitConsent` accepted a
  decision in any state, so `POST .../consent` with `granted:true` on a
  session no machine had joined set it to `consent_granted`. With the oracle,
  whoever guessed a code could consent in the helped person's place. It now
  requires `consent_requested`, which is what the branch's own tests assumed.

**How a session now moves:** an agent taking its place in the hub moves it
from `pending` to `connected`, recording its address and user agent, and the
server immediately requests consent. At the time the consent prompt was to
live in the Nest — a decision since superseded by the product model — so the
join page, polling `GET /api/sessions/{code}`, sees `consent_requested`
together with who is asking and for which permissions, and answers with
`POST .../consent`. Those details
are disclosed only in that state. A reconnecting agent changes nothing and is
not charged against its redemption budget. `TestConsentFlowEndToEnd` drives
the whole path through HTTP alone.

**Superseded direction.** All of this was built for the earlier model, in which
the helper created the session and the helped person answered consent from a
web page. In the product model the helped person's Chirp allocates the code and
shows the consent prompt itself, so `POST /api/sessions` (helper creates),
`POST /api/sessions/{code}/consent` (web page answers) and the consent details
in `GET /api/sessions/{code}` are all on the wrong side. The security properties
established here — every code-keyed entry point metered, consent refused until
requested — carry over unchanged; the endpoints themselves do not. **They are
gone:** barahn/chirp#5 removed them (barahn/chirp#13), and the surface that
replaced them is in §4.5. `GET /api/sessions/{id}` survives, keyed by session
ID instead of by code.

Also found: `TestSignallingCrossesBetweenPeers` failed 2 runs in 15 under CPU
load. A client's `Dial` returns when the server writes the upgrade response,
and the server joins the peer to the hub only afterwards, so an offer sent into
that window was refused with `ErrNoPeer` and dropped — and nothing told the
sender when to try again. Fixed in the protocol, not only the test: when the
second end arrives the relay sends both ends `chirp.peer_joined` naming the
other, and when one leaves the other gets `chirp.peer_left`. **A client waits
for `chirp.peer_joined` before sending**; receiving it is proof the other end is
registered. The relay's own messages all live in the `chirp.` namespace
(`signalling/relay.go`), which keeps them apart from the peers' signals.

### 4.5 Adopting remotekit's `rendezvous`, and the direction inverted

Chirp now requires `github.com/barahn/remotekit` (`rendezvous` first shipped
in `v0.2.0`; the pin is in §5.5) and imports only `rendezvous` and
`bark` — both standard-library only, so no new transitive dependency and never
`tunnel` (yamux, §5.5).
`session/code.go` and `session/redemption.go` were deleted.

**The flow, as the server implements it:**

1. A Chirp starts: `POST /api/peers {name}` → `peer_id`, `code`,
   `formatted_code`, `link`. The `peer_id` is its credential and is returned
   only to it. It opens its owner socket, `GET /ws?role=owner&peer=ID`, and
   keeps it for as long as it runs. `GET /api/peers/{peer}` returns the code to
   show now (the start code is single-use and replaced once used or expired);
   `DELETE /api/peers/{peer}` on exit releases its codes and link and ends its
   session. A Chirp that exits without `DELETE` is released the same way by
   the reaper once its owner socket has been closed (or never opened) for
   `DefaultPeerGrace`, 2 minutes (barahn/chirp#37).
2. Another Chirp types the code: `POST /api/redeem {code, name}` → session, or
   uses the link: `POST /api/links/{token}/sessions {name}` mints a single-use
   code and redeems it in one step. Both are metered per origin from one
   budget; unknown, expired and malformed codes are all `404`, throttled `429`,
   owner busy `409`. It joins with `GET /ws?role=controller&session=ID`.
3. When both ends are in the hub — whichever arrives second — the session moves
   `pending → connected → consent_requested` and the owner's socket receives
   `chirp.consent_request`, carrying remotekit's `bark.ConsentRequestPayload`
   (its `technician_name` is the controller's typed name) and
   `name_verified: false`.
4. The owner answers `POST /api/peers/{peer}/consent` with a
   `bark.ConsentResponsePayload`. It applies only to that peer's current
   session, only if `session_id` matches, and only in `consent_requested`.

**Deviation from the plan, deliberately:** the consent answer goes over HTTP,
authenticated by the peer ID, not up the owner's socket. The relay forwards
what a peer sends without parsing it, and answering on the socket would make
it parse the owner's messages. `TestConsentFlowEndToEnd` drives the whole flow
over HTTP and WebSocket only.

### 4.6 The lookup: the blind server's half of decision 5 (barahn/chirp#42)

The same server also offers the **lookup** that decision 5 in
`docs/product-model.md` reduces the public server to. It sits on the same
`SessionManager`, so codes, links, the throttle, the registration cap and the
peer grace are the same code, not copies.

1. The owner registers as in §4.5, step 1, then says how it can be reached
   over Nostr: `PUT /api/peers/{peer}/contact {key, relays}`. `key` is its
   per-session Nostr public key (64 lowercase hex), `relays` 1 to 8
   `ws://`/`wss://` URLs; anything else is `400`. It sends a new contact
   whenever it makes a new session key. It keeps its owner socket open, but
   only so the server knows it is running (decision 1, the peer grace): the
   lookup relays nothing over it.
2. The controller sends the code's routing part: `POST /api/lookup {code}`, or
   uses the link: `POST /api/links/{token}/lookup`. Either returns `{key,
   relays}` and nothing else. The code is spent exactly as `Redeem` spends it
   (a start code is replaced, a minted one is gone), and failures are metered
   from **the same per-origin budget** as `Redeem`, so the lookup is no cheaper
   way to sweep codes. No session is opened and the owner is not marked busy.
   An owner that set no contact answers `409`.
3. From there the two Chirps meet over Nostr (barahn/chirp#43) and bind each
   other with the PAKE over the code's secret part (barahn/chirp#21). The
   server never sees either.

`TestLookupFindsTheOwnerByCodeAndByLink` asserts that a lookup, by code and by
link, sends nothing to the owner's socket. The server only ever sees the six
routing digits; the four secret ones are the owner's Chirp's own (§4.8).

**Known limits:**

- **One controller per owner at a time.** Deliberate for now.
- **A peer away from its owner socket for 2 minutes is released**
  (maintainer decision, `DefaultPeerGrace`, tunable with `SetPeerGrace`;
  barahn/chirp#37). `serveOwner` reports the socket opening and closing
  (`OwnerAttached`, `OwnerDetached`), and the reaper, every 10 s, releases a
  peer detached past the grace: codes, link and session, as `DELETE` does. It
  checks and removes under one `sm.mu`, so a peer attaching meanwhile is never
  released while attached; one released meanwhile gets its socket closed. A
  link therefore stops working at most grace + 10 s after its Chirp vanishes
  (decision 1). `Reap` runs a pass on demand.
- **At most 30 open sessions per controller origin** (maintainer decision,
  `DefaultMaxSessionsPerOrigin`, tunable with `SetMaxSessionsPerOrigin`). A
  session counts until it ends, is denied, or its undecided deadline passes.
  The check runs before the code is consumed, so a refused redemption (`429`)
  leaves the owner's code usable. Behind `Server.ClientIP` the same caveats as
  the throttle apply: a NAT shares the 30.
- **At most 30 registered peers with a live code per origin** (maintainer
  decision, `DefaultMaxPeersPerOrigin`, tunable with `SetMaxPeersPerOrigin`;
  barahn/chirp#14). Every registration holds a code, so without a cap one
  origin could exhaust the 900,000-code space (`rendezvous.ErrExhausted` →
  `503`) and make random guesses likelier to hit. The 31st `POST /api/peers`
  gets `429`. The cap counts live codes, not registrations: a Chirp that exits
  without `DELETE` gives its place back when its code expires, ten minutes
  later. Replacing a lapsed code in `GET /api/peers/{peer}` takes a place
  again and gets `429` over the cap; otherwise an origin could register to the
  cap, let the codes lapse, register more and revive them all. Such a peer
  still exists, keeps its owner socket and its link. The origin is the same
  `Server.ClientIP` as the throttle, with the same NAT caveat.
- Controller identity is self-asserted by design (`docs/product-model.md`).

### 4.7 Signalling over Nostr relays: the carrier half of decision 5 (barahn/chirp#43)

With `Client.Nostr` set (via `-nostr` or `CHIRP_NOSTR`, a comma-separated list
of Nostr relay URLs), Chirp shifts signalling from the server to public Nostr
relays:

1. **Owner (`nostrOwner`):** When registered, the owner listens on the
   configured Nostr relays under a key generated for that registration
   (`nostr.Listen` from remotekit's `signal/nostr`). It registers this contact
   (`key` and `relays`) with the server via `PUT /api/peers/{peer}/contact`. An
   initial code is held back (`awaitListening`, up to 10s) until the contact is
   registered, so an immediate lookup does not find an empty contact. If all
   relays disconnect, it listens under a new key and updates the contact.
2. **Controller (`helpOverNostr`):** When helping via code or link, the
   controller queries the server's lookup (`POST /api/lookup` or
   `POST /api/links/{token}/lookup`) to retrieve the contact, then dials the
   owner directly on Nostr via `nostr.Dial`.
3. **Knock protocol:** Before remotekit handles the WebRTC session, the two
   Chirps exchange out-of-band dotted messages:
   - `TypeAskConsent` (`consent.request`): Controller asks to connect with its
     asserted name.
   - `TypeConsentAnswer` (`consent.answer`): Owner answers (granted, declined,
     busy, or expired).
   - `TypeSessionEnd` (`session.end`) / `typeClose` (`close`): Session
     termination and controller disconnect.
4. **Data channel enforcement:** Because Nostr payloads must fit NIP-59 gift
   wraps and public relays should not carry bulk traffic even encrypted,
   sessions signalled over Nostr keep input, clipboard and files strictly on
   WebRTC data channels (`RequireDataChannel(true)` on `stream.Runner`), and
   `DisableRelayFallback(true)` stays on.
5. **Relay visibility:** Relays see only NIP-59 gift wraps (kind 1059)
   encrypted to ephemeral keys via NIP-44 v2. The server performs only code
   registration and lookup, seeing no session signalling.
6. **Coexistence:** An owner listening on Nostr can still be helped through the
   traditional server relay by a client without Nostr configured.

**Known limits, and what #43 still needs:**

- **The ends are bound by the PAKE** (§4.8): a key the lookup returns that
  is not the owner's fails the PAKE, so the lookup is no longer trusted.
- **`signal/nostr` is tagged.** Chirp pins `signal/nostr/v0.1.0`, the
  module's first release, which requires remotekit `v0.6.0`, and remotekit
  `v0.6.1`, the first release with `pake`.
- **Relays are not redialled** (barahn/remotekit#70): when every relay drops,
  the owner listens again under a new key and registers it, and a session in
  progress ends. **NIP-42 auth** (barahn/remotekit#71) is not supported, so
  relays that require it cannot be used.
- **No default relay list.** `-nostr` must be given; there is no public
  network yet (decision 5).
- **The key lives for a registration**, not for one session: it changes with
  every new code asked for (and after a session, which asks for one), and
  when the relays drop.
- A request over Nostr is open for **2 minutes** (`nostrAskFor`), then the
  prompt declines by itself.

### 4.8 The PAKE over the code's secret part (barahn/chirp#21)

Over Nostr, the code is **6 + 4 digits**, `482-913-5071` (decision 5). The six
route: the server sees them. The four are made by the owner's Chirp
(`secretBook`, `client/pake.go`) and never leave the two people: they are the
password of a PAKE, remotekit's `pake` — CPace, draft-irtf-cfrg-cpace-21,
from [`mendsec/cpace`](https://github.com/mendsec/cpace) — whose review is in
barahn/remotekit#96. The link carries its own four after a dot
(`<token>.0042`), and the site's link page accepts that form.

1. **Before anyone is asked,** the controller sends `pake.start`, naming the
   routing part it used (or the link). The owner answers `pake.reply` under
   that code's secret, which it then forgets: **one attempt per code**. The
   controller checks the owner's proof, sends `pake.confirm`, and only then
   `consent.request`; the owner checks the controller's proof before it shows
   any prompt.
2. **Each end comes out with the other's ed25519 key**, proved by the code.
   The session is signed with them: the owner's runner signs its answers and
   acts only on offers the controller signed (`RequireSignedViewers`); the
   controller's viewer accepts answers only from the owner's key
   (`AgentKey`). The CPace inputs are the secret, a context naming the code or
   link, and the two Nostr keys of the attempt as the session ID.
3. **A failure shows at both ends** (docs/ux.md, Messages): the controller's
   window says the last four digits don't match, and the owner's says the
   same as it shows the code that replaced the spent one.
4. **Guessing is bounded.** A code is spent by the lookup and its secret by
   one PAKE, so each guess costs a code, metered per origin by the server.
   The link mints codes, so its secret could otherwise be guessed one attempt
   at a time: after `maxLinkFailures` (3) failed or abandoned PAKEs through
   it, the owner gives the link up with the code, as *New code* does. A PAKE
   left unconfirmed for `nostrPakeFor` (20 s) counts as failed.
5. **The trusted relay path is unchanged:** it has no PAKE and no signed
   viewers. A Chirp without `-nostr` given a ten-digit code uses its six
   routing digits.

**Known limits:** remotekit is pinned at the merge of barahn/remotekit#107
(a pseudo-version past `v0.6.0`, which predates `pake`) until the next
remotekit release; the owner's signing key lives for a registration, as its
Nostr key does; and an owner without Nostr shows six
digits, which a helper with Nostr cannot use (it says the code is
incomplete, before spending anything).

### 5.5 The remotekit boundary in practice

Chirp consumes remotekit's `rendezvous` and `bark` packages (§4.5); the rest
below still describes what `cmd/chirp` will need. This section records what an
audit of the two trees actually found, so the next agent does not have to
re-derive it.

**What remotekit already provides** (Apache-2.0, ~15k lines, 14 packages):
`screen` with capture for X11/Wayland/Windows/macOS plus damage detection and a
pure-Go VP8 encoder whose reconstruction is byte-exact against libvpx;
`webrtc` (`PeerSession` over pion, video track, `SignalMessage`); `input`;
`clipboard`; `transfer` (chunked, resumable); `tunnel`; `tray`; `service`;
`osinfo`; `bark` (the shared wire envelope); `heartbeat`.

**`tunnel` is not Chirp's relay, and this is the important negative result.**
It is built around enrolment: pairing codes, persistent agent credentials, an
agent registration store, agent IDs, online status. That is precisely the
standing-agent model Chirp rejects in its first paragraph. Do not try to reuse
it for session signalling; the `signalling` package writing its own two-peer
hub is the correct call, not duplication.

**But `tunnel` was also where consent was enforced. DONE: remotekit moved it
out, into `stream` (barahn/chirp#20, barahn/remotekit#83, released in
`v0.4.0`).** Since remotekit Phase 0–2,
`tunnel.AgentStreamRunner` holds `Grant`, `RequireScreenViewConsent` and
`RequireSignedViewers`. It also holds the Phase 2 transport seam:
`tunnel.SignalConn` and `AgentStreamRunner.Serve(ctx, conn)` run a whole
session over any transport (barahn/remotekit#68, #77). Keeping `tunnel` out of
Chirp would have meant re-implementing consent enforcement; importing it would
have meant taking yamux (MPL-2.0, below) and the enrolment code.

The maintainer chose option 1 of barahn/chirp#20, on 2026-10-08. remotekit
moves the session runner out of `tunnel` and into its own package, which
imports neither yamux nor the enrolment code: consent, viewer signing, the
data-plane rules, `SignalConn` and `Serve` (barahn/remotekit#83). The split runs along a line
the code already has. yamux is imported only by `client.go`, `server.go` and
`tunnel.go`. The runner's only tie to enrolment is `AgentCredentials`, of
which `Serve` uses just `AgentID` and `DeviceKeyPath`, so the new package
takes an explicit ID and an in-memory signing key instead. `tunnel` keeps
`Start` and wraps the new runner, so Barahn does not change.

remotekit `v0.4.0` shipped it as **`github.com/barahn/remotekit/stream`**, and
Chirp pins remotekit past `v0.6.0`, at the merge of barahn/remotekit#107
(§4.8). `stream.New(stream.Config{ID, SigningKey, PeerConfig})`
builds a `stream.Runner`, and `Serve(ctx, conn)` runs it over any
`stream.SignalConn`. The runner holds consent (`Grant`, `Revoke`,
`RequireScreenViewConsent`), `RequireSignedViewers`, and the data-plane rules
(`RequireDataChannel`, `DisableRelayFallback`). `PeerConfig` takes Chirp's own
STUN/TURN servers (`docs/stun-turn.md`). `stream` depends on neither `tunnel`
nor yamux, and a remotekit test keeps it that way.

What this commits Chirp to:

- **Chirp still never imports `tunnel`.** The licence gate keeps flagging
  MPL-2.0 for review, and nothing in Chirp should ever need the exception.
- **Chirp does not enforce consent itself.** `cmd/chirp` drives remotekit's
  runner from `stream`: it grants what the owner accepted in the prompt
  (barahn/chirp#11), and serves the session over a `SignalConn` on Chirp's
  relay socket (barahn/chirp#12). A second implementation in Chirp would drift
  from Barahn's.
- **Pinned at a release, with one exception for now.** barahn/chirp#20 is closed, and #12
  builds on `stream`. remotekit `v0.5.0` shipped what the controller needs:
  `stream.Viewer`, the receive side of `webrtc` and the `vp8` decoder
  (barahn/remotekit#87: #88, #91, #92). `v0.6.0` adds the viewer's
  clipboard, files and monitor selection, and the runner's viewer events,
  `Disconnect` and received-file controls (barahn/remotekit#93, #94, #97,
  #98), which #77 and #79 build on. Until then `go.mod` pinned a commit of a
  remotekit feature branch that never reached `develop`; pin release tags
  only, so every build resolves from a ref the repository keeps. The one
  exception is current: `pake` (§4.8) is not in a remotekit release yet, so
  `go.mod` pins the merge of barahn/remotekit#107, a pseudo-version past
  `v0.6.0`. Pin the first release that includes it.

**remotekit's Phase 2 did not build the `Signaler` its plan proposed.** It
shipped the narrower `SignalConn` above, and **`signal/nostr`**: a separate Go
module carrying a session's signalling over public Nostr relays, gift-wrapped
and encrypted end to end with per-session keys (barahn/remotekit#77). Any
Chirp document that places future work "alongside the Phase 2 `Signaler`"
means `SignalConn` and `signal/nostr`.

**What the signalling branch genuinely duplicates: almost nothing.** Its `Hub`
never parses what it forwards — `Forward` relays opaque bytes by design — so it
does not reimplement `webrtc.SignalMessage` encode/decode. Two narrow seams are
worth closing before it merges:

- ~~`encodeError` emits `{"type":"error",...}` into the same namespace as
  remotekit's `SignalType`.~~ Closed: relay messages now use
  `signalling.RelayErrorType` = `"chirp.error"`. A dotted value cannot collide
  with remotekit's bare-word types, and names the relay as the sender.
- Nothing pins Chirp's two *ends* to remotekit's envelope. The hub does not
  care, but the technician viewer and the agent must agree, and today only
  prose says they will.

**The finding that matters most.** remotekit ships
`webrtc/signed.go`: a signed `SignalMessage` — ed25519, domain-separated
canonical bytes (length-prefixed, not JSON, so a browser can reproduce them),
bounded lifetime, clock-skew tolerance and a replay-blocking `NonceCache`.
Signing is opt-in and the fields are `omitempty`, so adopting it breaks no
existing receiver.

Read `remotekit/docs/decentralised-signalling.md` for why it exists: a
signalling server is a man-in-the-middle with total power over a session, and
signing at the endpoints is what demotes the carrier from *trusted component*
to *transport*. That bears directly on one of Chirp's three design
commitments — "any hosted service is a convenience, never a requirement". A
hosted Chirp relay that the endpoints cannot verify around is not a
convenience; it is the trusted third party the commitment says it must not be.

**Is an untrusted relay required? No — correcting an earlier version of this
section.** It argued that a hosted relay the endpoints cannot verify around is
"the trusted third party the design commitment rules out". The commitment says
something narrower: *anyone may run their own relay; a hosted service is a
convenience, never a requirement.* Self-hosting satisfies it. A self-hosted
relay sits on the controlling user's side, whom the controlled user already
trusts with their machine, and anyone unwilling to trust a hosted relay runs
their own. Barahn works the same way, as does every mainstream remote-support
tool. So a relay its users run or trust is trusted, openly. A public relay
run for strangers is the case the commitment does not cover, and for it what
follows is **required**, not optional: see the decision below.

> **Decided (barahn/chirp#19, 2026-10-08): not for the first runnable Chirp,
> yes before any public relay** (`docs/product-model.md`, decision 5). The
> MVP ships with this trusted relay. Before Chirp offers a public one, the
> public server becomes blind: a lookup that maps a code's six-digit routing
> part to the owner's session key and relays (barahn/chirp#42), signalling
> over Nostr relays through remotekit's `signal/nostr` (barahn/chirp#43), and
> a PAKE over the code's four-digit secret (barahn/chirp#21). All three are in
> the *Blind public network* milestone. barahn/chirp#7's "every Chirp is a
> node" was not adopted: Nostr relays already give a carrier that sees
> nothing, without a node network to design.

**Correction: signing is necessary, not sufficient.** An earlier version of
this section said remotekit "already has the parts". It does not. A signature
proves a message came from the holder of a key; it removes trust in the relay
only if each end already knows the other's key by a route the relay does not
control. Barahn has that route — an agent generates a keypair at enrolment and
the key is pinned then. Chirp has no enrolment. Technician and helped person
meet for the first time, and if their public keys travel through the relay, a
malicious relay substitutes its own and signs everything itself: every
signature verifies, and proves nothing.

**What binds the keys is a PAKE over a secret the relay never sees.** A
password-authenticated key exchange lets two parties who share a short secret
agree on a key such that an impersonator gets exactly one guess per attempt,
learns nothing it can test offline, and fails visibly. That key then
authenticates each end's signing key, and remotekit's `signed.go` — with its
`NonceCache` — carries every signal after that. This is the shape
magic-wormhole uses for the same first-contact problem.

**The hard constraint: today the relay sees the whole PIN.** The agent joins
with `/ws?code=`, and the relay routes by that code. A relay that knows the
secret runs the PAKE with both ends and is the man in the middle again.
Hashing the code does not help — 900,000 values invert instantly. So an
untrusted relay requires **splitting the code** into a routing part the relay
sees and a secret part used only in the PAKE and never sent to the relay.
magic-wormhole's codes are exactly that: a nameplate for routing, words for the
secret. For Chirp it means the code a technician reads aloud gets longer, or
its six digits are divided — a product decision, not an implementation detail.

The plan, with what decision 5 settled:

1. **The code format — decided: 6 + 4 digits**, read as `482-913-5071`. Six
   for routing, which the lookup sees; four for the secret, which nothing
   but the two people ever sees. A relay in the middle gets one guess in
   10,000 per attempt, and a failed PAKE is visible to both ends.
2. **Choose the PAKE — done** (barahn/chirp#21, §4.8). None of the three
   below passed review against draft-irtf-cfrg-cpace-21 (barahn/remotekit#96),
   so CPace was assembled on gtank/ristretto255 and checked against the
   draft's vectors, in its own module, `mendsec/cpace`; remotekit's `pake`
   binds the ed25519 keys over it. The survey as it stood: CPace (an IETF
   CFRG draft) is the natural candidate, SPAKE2 the alternative. A Go implementation must be
   vetted — maintenance, review history, test vectors against the draft, and a
   permissive licence through the licence gate. Do not hand-roll it. Surveyed
   on 2026-09-30 from the module proxy, not yet audited:

   | Module | Licence | State | Notes |
   | --- | --- | --- | --- |
   | `github.com/bytemare/cpace` | MIT | active, no release tag | tracks the CFRG CPace draft; pulls `bytemare/ecc` and friends |
   | `filippo.io/cpace` | BSD-3 | last commit Jan 2021, no tag | early draft over ristretto255; unmaintained |
   | `github.com/schollz/pake/v3` | MIT | tagged v3.2.0 | SPAKE2-style, used by croc; default curve is the non-standard `siec` |

   The PAKE is mechanism, so it belongs in remotekit, through remotekit's
   licence gate.
3. **Then the protocol:** each end runs the PAKE over the Nostr connection
   (barahn/chirp#43) as opaque messages, sends its ed25519 public key
   authenticated under the PAKE key, and from then on every signal is a
   remotekit `SignalMessage` signed and verified against the pinned key,
   replay-checked with `NonceCache`.
4. **Relay messages stay unauthenticated** — they come from the relay by
   definition — so an end must treat `chirp.*` messages as hints (presence,
   errors) and never act on them for anything security-relevant. Clients tell
   them from forwarded signals by the prefix alone, so the hub refuses to
   forward any payload typed `chirp.*` (`ErrReservedType`): otherwise either
   end could forge one, as a controller sending `chirp.peer_left` would stop
   the owner's runner while staying connected (found in review of
   barahn/chirp#60).

This is why decision 5 cannot be met by adopting `signed.go` alone.

One caveat when reading that document: its status line says "proposal, not
accepted. Nothing here has been implemented", and for its Phase 0 item 3
("Extend `SignalMessage` with `PubKey`, `Nonce`, `IssuedAt`, `ExpiresAt` and
`Sig`, plus `Sign()`/`Verify()` and a seen-nonce cache") that is simply out of
date — `webrtc/signed.go` implements exactly that. Trust the tree over the
status line.

**remotekit's pipeline, and a licence fact that constrains Chirp.**
barahn/remotekit#20 brought remotekit the same DevSecOps layers Chirp has —
least-privilege workflows, harden-runner, gitleaks over the full history,
CodeQL and dependency review gated on `CODE_SCANNING`, an SBOM, Dependabot,
`SECURITY.md` — plus a dependency licence gate it lacked. That gate's first run
found `github.com/hashicorp/yamux` is **MPL-2.0**, which remotekit's own policy
does not allow; it was excepted by name there at first, and has since been **accepted
formally** by the maintainer — barahn/remotekit#24, merged, moved the gate to an exact
licence list that includes MPL-2.0. For Chirp the consequence is precise: **only
remotekit's `tunnel` package pulls in yamux.** `screen`, `input`, `clipboard`,
`transfer` and `webrtc` — everything `cmd/chirp` needs — are clean. Chirp's
licence gate reads imported packages (`go list -deps`), not the whole module
graph, so it stays green as long as Chirp never imports `tunnel`; if it ever
did, the gate would flag MPL-2.0 for review. That is a second reason, after the
enrolment model, to keep `tunnel` out of Chirp.

**Where the rest of the dependency will appear:** `cmd/chirp`. It needs
`screen`, `input`, `clipboard`, `transfer` and `webrtc.PeerSession`. `session/`
needs only `rendezvous`, and should acquire nothing more.

### 5.6 The UI library: Fyne — DECIDED (barahn/chirp#24)

The maintainer chose **Fyne** (`fyne.io/fyne/v2`) for `cmd/chirp`'s UI. Chirp
needs windows, not only a tray icon: one window shows the machine's own code
and link, one has a field to type a code or paste a link, and the consent
prompt has to be drawn by Chirp, the same way on every platform, unmistakable
enough that an unexpected one is declined. Fyne draws all of that itself, and
brings its own tray (`fyne.io/systray`).

**What was checked**, in a throwaway module built against each candidate,
before deciding:

| | Draws windows | Modules imported | Licences | Builds with `CGO_ENABLED=0` |
| --- | --- | --- | --- | --- |
| Fyne v2.8.1 | yes | 26 | all permissive (BSD, MIT, Apache-2.0, ISC) at module level; its embedded fonts are not (barahn/chirp#54) | none of Linux, Windows, macOS |
| `fyne.io/systray` | no, tray only | 2 | permissive | Linux and Windows; not macOS |
| `getlantern/systray` | no, tray only | 9 | permissive | Windows only (GTK + appindicator on Linux) |

remotekit's `tray` was ruled out. It is built for the standing agent: its
constructor takes an agent ID and a server address, its menu shows them, and
on Windows it imports remotekit's `service` package (OS service installation).
It draws no windows either, so the consent prompt would still be missing.

**What the decision costs, and where it lands:** Fyne needs cgo on every
platform, and on Linux the X11 and OpenGL development headers. CI's
*Cross-compile Check* builds `./...` for Windows and macOS with
`CGO_ENABLED=0` from a Linux runner, and that cannot build a Fyne program. The
pull request that adds `cmd/chirp` (barahn/chirp#10) has to move its build to
native runners per OS (a matrix of `ubuntu`, `windows` and `macos`), or keep
the cross-compile check for the library packages and build `cmd/chirp`
natively. `THIRD_PARTY_NOTICES.md` grows by Fyne's tree in that same pull
request, and the licence gate re-checks it there. The library packages
(`session`, `signalling`) must not import Fyne. Keep the UI in `cmd/chirp`,
or a package under it, so the relay still builds without cgo.

## 6. Hard constraints — do not trade these away

**Product commitments** (from `README.md`, stated as constraints on what Chirp
may become):

- **No feature gates.** Screen sharing, input control, multi-monitor, file
  transfer and clipboard sync are the free core, permanently. Never add a
  licence check, tier check or entitlement lookup around any of them.
- **Explicit consent.** A session cannot start without the end user agreeing on
  their own machine, in a prompt Chirp controls. No "unattended mode", no
  pre-authorisation, no consent bypass flag — not even behind a config key.
- **Self-hostable with zero restrictions.** Anyone may run their own signalling
  and relay. Any hosted service is a convenience, never a requirement. No
  phone-home, no mandatory endpoint.

**Licensing and dependency constraints:**

- Every new Go file starts with:
  ```go
  // SPDX-License-Identifier: AGPL-3.0-only
  // Copyright (C) 2026 Fabrintek Engenharia Digital Ltda
  ```
- **No copyleft dependencies.** Chirp is AGPL, so a GPL/AGPL dependency would
  be licence-*compatible* and still unacceptable: Fabrintek relicenses Chirp
  for its proprietary platform on the strength of owning all of Chirp, and it
  owns none of its dependencies. Permissive only (MIT/BSD/Apache-2.0). CI
  enforces this via `scripts/gen-third-party-notices.sh`; after any dependency
  change, re-run it and commit `THIRD_PARTY_NOTICES.md`. The one exception is
  the fonts Fyne embeds: the maintainer accepted the SIL OFL 1.1 and the
  Bitstream Vera licence for them (barahn/chirp#54). They stay under their own
  licences, and the script gates every embedded font one by one, so a font a
  dependency adds later fails the build until it is reviewed. The Warm look's
  own fonts (`cmd/chirp/internal/warm/fonts/`) are OFL too: the only files in
  this repository Fabrintek does not own (LICENSING.md).
- **Dependencies point inwards only.** remotekit depends on neither of the
  others; Chirp may depend on remotekit; the Barahn platform may depend on
  both. A change that needs the arrow reversed is a design problem, not a
  licensing exception.
- **Contributions are closed.** Do not merge external pull requests. The DCO
  sign-off CI check is *not* CLA acceptance and must never be described as
  such.

## 7. Working agreement

- Small, reviewable commits with Conventional Commit subjects
  (`feat(session):`, `fix(session):`, `ci:`, `docs(legal):` — follow the
  existing log).
- Every commit signed off: `git commit -s`.
- Tests alongside behaviour; run `go test -race ./...` and `go vet ./...`
  locally before pushing. Prefer a failing test first for each defect in
  section 4.
- Keep `README.md`'s "Status" section honest. It currently says Chirp is not a
  runnable product; when that stops being true, it is part of the same change
  to say so.
